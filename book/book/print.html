MPDFM

MPDFM — MPD File Manager

MPDFM is a terminal application for managing an MPD music library: edit tags, and re-organize directories without breaking your playlists.

Why it exists

MPD identifies every track by its path relative to music_directory, and that path is copied into every .m3u in your playlist directory and into the saved queue in MPD’s state file, so a plain mv silently breaks both. MPDFM makes moving a file and rewriting every reference to it one transaction: previewed first, backed up and journaled before the first change, and reversible byte for byte. If it is killed halfway, mpdfm recover finishes or rolls back what it started — and Safety and recovery says how to do the same by hand.

Start here — nothing in these two writes a byte

$ mpdfm doctor                                           # what is wrong, today
$ mpdfm move --dry-run "hiphop/MF DOOM" "hiphop/Doom"    # what a move would do

doctor reports broken playlist references, missing tags, inconsistent albums and the like, and says plainly when the library is fine. --dry-run prints the same preview that appears before every commit: the moves, each playlist line that changes, and anything that would stop it. Run those on your real library first, then try your first real command on a copy.

Where to go next

  • New here? Install and do a first run.
  • Want to do something? The Guide has a page each for moving, tags, organizing, cover art and undo.
  • Prefer a full-screen interface? See the TUI.
  • Worried about your library? Read Safety and recovery.
  • Looking up a flag? The command-line reference is generated from the program itself, so it always matches the version you have.

What it will and will not do

  • MPD is optional. With it running, MPDFM asks it to rescan after a commit and warns about moved files that are in the live queue. Without it, MPDFM rewrites the saved queue in the state file itself.
  • It never overwrites. A move that would land on an existing file is a conflict, reported before anything happens.
  • It does not guess. A path that is not valid UTF-8 is reported and skipped. A playlist line is rewritten only on an exact path match; URLs, comments, #EXTINF lines and anything it does not understand are written back byte for byte.
  • It has a delete switch. delete_enabled = false makes every operation that would remove a file refuse.

Install

MPDFM needs a Rust toolchain (1.93 or later) and nothing else — tag handling is pure Rust, and MPD is optional.

$ git clone https://github.com/Celsuss/MPDFM && cd MPDFM
$ cargo install --path .          # puts `mpdfm` in ~/.cargo/bin

Man pages

Man pages are generated from the argument definitions, so they always match the binary:

$ mpdfm man | man -l -                                    # read it now
$ mpdfm man --dir ~/.local/share/man/man1                 # install: mpdfm.1 + one per subcommand

Afterwards man mpdfm and man mpdfm-move work.

First run

Check what MPDFM found, once:

$ mpdfm config show               # where it found your library, and why

MPDFM reads music_directory, playlist_directory and the state file from your mpd.conf, so on a normal MPD setup there is nothing to configure. If config show says otherwise, the configuration reference documents every setting, and --music-dir / --playlist-dir override anything for a single run.

Then look around without changing anything:

$ mpdfm scan                      # counts by format, album dirs, warnings
$ mpdfm doctor --full             # every finding, not the first ten

Paths in every command are relative to your music directory, which is what MPD’s own paths are.

The ground rules

  • Every command takes --json.
  • Every command that edits tags, moves or re-files takes --dry-run, which prints the preview and writes nothing.
  • Every command that changes the library asks before it commits. --yes skips the question, and is required when stdin is not a terminal.
  • Try your first real command on a copy of part of your library. See Safety and recovery for exactly what is backed up.

Moving and renaming

mpdfm move SRC DST moves or renames a file or directory and rewrites every reference to it — in every .m3u playlist and in MPD’s saved queue — as one transaction.

$ mpdfm move --dry-run "rock/Old Name" "rock/New Name"   # look first
$ mpdfm move "rock/Old Name" "rock/New Name"             # shows the preview, asks, commits
$ mpdfm undo                                             # changed your mind

The preview

Before anything is written you see the moves, each playlist line that changes, and anything that would stop the move. --dry-run prints that preview and stops.

What can stop a move

  • A conflict. A move that would land on an existing file is refused before anything happens; MPDFM never overwrites. Moving a directory onto one that exists needs --merge, which moves what does not collide.
  • The library changed since the preview. The commit is refused (exit code 2) rather than acting on stale information.
  • A path that is not valid UTF-8. It is reported and skipped.

Across file systems

A move between devices is a copy followed by a delete. --verify hashes every copy and reads it back, at the cost of a second read of each file.

How playlists are rewritten

A playlist line is rewritten only on an exact path match. URLs, comments, #EXTINF lines and anything MPDFM does not understand are written back byte for byte. Every playlist it touches is backed up first — see Safety and recovery.

See also the move reference.

Editing tags

$ mpdfm tag show -r "hiphop/Mac + Devin Go To High School"
$ mpdfm tag diff --genre "Hip Hop" --renumber-tracks -r "hiphop/Mac + Devin Go To High School"
$ mpdfm tag set  --genre "Hip Hop" --renumber-tracks -r "hiphop/Mac + Devin Go To High School"
  • tag show prints the tags of a file, or of every audio file in a directory.
  • tag diff shows what tag set would change, and writes nothing.
  • tag set previews the change, asks, then writes.

-r / --recursive includes audio files in subdirectories.

Setting fields

--title, --artist, --album-artist, --album, --year, --track, --disc, --genre, --comment and --composer set a field on every selected file. --clear FIELD removes one entirely.

Bulk helpers

FlagEffect
--renumber-tracksnumber the selected files 1..n in listed order and set the total
--title-from-filenametake each title from the file name, stripping a leading track number and the extension
--album-artist-from-artistgive each file its own artist as its album artist
--strip-commentremove the comment from every selected file
--trim-whitespacestrip leading and trailing space from every text field

What does not change

Nothing else in a file changes when its tags do: embedded artwork, ReplayGain, MusicBrainz ids, lyrics and every unknown frame survive, and the audio stream is bit-identical. The original file is backed up before it is rewritten.

See also the tag reference.

Organizing to a template

mpdfm organize re-files tracks into paths derived from their tags, rewriting every playlist reference on the way — the same transaction as move.

$ mpdfm organize --dry-run --limit 20          # a cautious first look
$ mpdfm organize --limit 20                    # the first twenty tracks' worth
$ mpdfm organize --only-missing                # then the rest, whose tags are complete

The default template is

{genre}/{albumartist}/{year} - {album}/{track:02} {title}

Change it with -t / --template, or set organize_template in the configuration. A track whose tags the template cannot fill is left where it is and listed — never filed under “Unknown”.

Template syntax

A template is /-separated segments of literal text and {fields}. The source file’s extension is always appended to the last segment.

FieldValue
artistthe track artist
albumartistthe album artist, falling back to artist
album, title, genreas tagged
yearthe leading four digits of the date
track, discthe number, without its total
extthe source file’s extension, without the dot
original_dirthe directory the file is in now — a whole segment on its own
filenamethe file’s current name, without its extension

A multi-valued tag renders joined with ; .

FormMeaning
{track:02}zero-pad a number to two digits (year, track, disc)
{artist:upper}, :lower, :titlechange case (text fields)
{album?}when album is absent, leave out the whole segment
{genre|Unsorted}when genre is absent, use Unsorted
{{, }}a literal brace

A field written plainly is required: a file without it stays where it is. ? and |default are the explicit opt-ins to place it anyway.

Multi-disc sets

When a file is one disc of several and the template does not place the disc itself, a Disc N directory is added in front of the file name. A file that is clearly one disc of several but has no disc number is unplaceable.

Working through a big library

  • --limit N stages at most N tracks’ worth of moves.
  • --only-missing only moves files whose tags are complete for the template and that are not already in place.
  • --no-aux moves tracks only; cover art, .nfo and .cue files stay put.

See also the organize reference.

Cover art

$ mpdfm cover show "rock/Album"                # embedded and loose art, and what disagrees
$ mpdfm cover set --dry-run "rock/Album"       # embed the album's cover.jpg in every track
$ mpdfm cover extract "rock/Album"             # or write the embedded one out as cover.jpg
$ mpdfm cover remove "rock/Album"              # remove the embedded front cover
  • show lists embedded and loose art for a track or album directory and what disagrees between them.
  • set embeds an image as the front cover of every track in the album, replacing any front cover already there.
  • extract writes the album’s embedded cover out as an image beside its tracks.
  • remove removes the embedded front cover from every track, leaving any other pictures.

Cover art is decoded for JPEG and PNG. In the TUI it is drawn in kitty, iTerm2/WezTerm and sixel terminals, and as a plain placeholder everywhere else (never inside tmux).

See also the cover reference.

Undo and recover

Undo

Every change is a journaled transaction, and every transaction can be reversed byte for byte as long as what it touched has not changed since.

$ mpdfm undo --list                         # what can be undone
$ mpdfm undo                                # the most recent
$ mpdfm undo 20260924T224500Z-00a3f1        # a specific one

If something has changed since, undo says so and refuses. --force reverses everything that is still safe to reverse and reports what it skipped.

Recover

If MPDFM is killed halfway through a commit, the journal knows. recover surveys what was left and rolls it back (the safe default) or finishes it:

$ mpdfm recover                              # survey, then roll back what a crash left
$ mpdfm recover --forward                    # finish it instead
$ mpdfm recover 20260924T224500Z-00a3f1

If mpdfm itself will not run, Safety and recovery has the same recovery by hand.

See the undo and recover references.

Working with MPD

MPD is optional and never fatal.

  • Configuration. MPDFM reads music_directory, playlist_directory and the state file from your mpd.conf. See Configuration for the order in which sources are consulted.
  • MPD running. After a commit MPDFM asks it to rescan, and warns about moved files that are in the live queue. It speaks a minimal protocol client, just enough for update and status.
  • MPD not running (or --no-mpd). MPDFM rewrites the saved queue in MPD’s state file itself.

Either way, playlists in the playlist directory are rewritten in the same transaction as the move.

The idea in four steps

Every job in the TUI has the same shape:

  1. Find what you want — walk the tree, search or filter.
  2. Select it — mark files, or just leave the cursor on one.
  3. Stage an operation — move, rename, delete, organize or edit tags. Staging only adds to a plan.
  4. Review and commit — the pending view shows every file that moves and every playlist line that changes. c commits; u undoes.

Nothing a key does touches the library until step 4, and the pending view draws the very preview mpdfm move --dry-run prints. The terminal is always given back, including after a panic or a kill.

A first session

Moving an album, from nothing:

  1. Walk to the album with j/k and l/h (the tree follows you).
  2. Press r. The command line opens as :move hiphop/MF DOOM - Mm..Food. Edit the path to the new name and press enter.
  3. Press p. You see the move and the playlist lines it rewrites. Expand a playlist with enter to read the exact -/+ lines.
  4. Press c to commit. A message gives the transaction id.
  5. Wrong? Press u.

Browsing and marking

The panes

  • Tree (left) — directories. The row under its cursor is the directory whose contents the middle pane shows, so the two can never disagree.
  • Listing (middle) — the files in that directory, with duration and bitrate when there is room. Non-audio files (folder.jpg, .nfo, .cue, logs) are shown dimmed on purpose: they are what travels with an album when you move it.
  • Details (right, 90 columns or wider) — tags, size and format of the focused entry, and which playlists refer to it. The cover art is drawn here in terminals that support it (kitty, iTerm2/WezTerm, sixel; a placeholder elsewhere, and never inside tmux).

tab switches focus between the tree and the listing.

A ⚠ next to an entry means a playlist refers to it (or, on a directory, to something inside it), so you can see what a move would touch before staging it. Files that are not valid UTF-8 are counted in a badge rather than silently left out.

Staging moves, renames, deletes and organize

These keys stage an operation: they add it to the pending plan and change nothing on disk. Stage as many as you like, in any order, then review and commit them together in the pending view as one transaction.

All of them act on the marks, or on the row under the cursor when nothing is marked. Playlists and MPD’s saved queue are rewritten as part of the same transaction, just as for mpdfm move.

Move: m

Mark things, walk to the directory they belong in, press m. They are staged to move into the directory you are looking at. Moving something to where it already is stages nothing.

Rename or move to an exact path: r and :move

r opens the command line already filled in as :move <path of the row>. Edit the path and press enter; esc cancels. You can also type :move <dst> yourself.

With one thing selected, <dst> is its new path (a rename). With several, <dst> is a directory they move into.

Delete: d

Stages a delete of the marked files. A marked directory is left out with a message rather than expanded, because deleting a tree should not follow from one keystroke. Deletes can be switched off entirely with delete_enabled = false in the configuration, in which case the pending view refuses to commit them. Deleted files are kept in the journal’s backup and can be undone.

Organize: o or :organize

Opens a template line and a live preview of where the first twenty files would go, updated on every keystroke. A template that does not parse shows the error with a ^ under the offending character. Files whose tags the template cannot fill are listed as staying put.

Press enter to compute the whole mapping and stage it; esc cancels. The syntax is the same as the command line’s — see Organizing to a template. :organize <template> opens the view with the template already filled in.

Changing your mind

Nothing is on disk yet, so dd in the pending view drops one operation and x discards the whole plan. Quitting with operations staged asks first.

When the selected files disagree about a field, it shows <multiple>. Leaving it alone changes nothing. Validation

Year must be a number or a date, and track must be n or n/total. An invalid field shows its error inline and staging is refused until it is fixed. If any selected file is not writable, the editor names it before you stage.

Nothing is written when you leave a field — only when you stage and commit. A committed edit can be undone with u; the originals are backed up first, as with mpdfm tag set.

The pending view and committing

Press p from anywhere to see the plan: every operation you have staged, in order. This is the screen that exists so you can say yes knowing exactly what will happen.

(Illustrative.) It is the same renderer as mpdfm move --dry-run, so the two cannot disagree.

Reading it

  • j/k move the cursor; enter, space or l unfold a playlist into every line that changes (- old, + new), or a refused operation into its reason; h folds it again. The diff is complete, not a count.
  • Conflicts are shown in red with the reason on each operation, and commit is disabled until they are gone. Typical causes: a move onto an existing file, or a destination two operations both want.
  • Warnings are not blockers — for instance, that a file is in MPD’s current queue and will need requeueing.

Acting on it

KeyDoes
ccommit the plan
dddrop the operation under the cursor, then re-validate (dropping one can clear — or cause — a conflict)
xdiscard the whole plan, after a confirmation
uundo the transaction that was just committed
escback to the browser; the plan stays staged

dd is doubled on purpose. d in the browser stages a delete, so a lone d here would mean the opposite thing.

Committing

A commit runs on a worker with a progress line, so the screen stays responsive on a big organize. esc cancels it while it is still before the first change to the library; after that it says so plainly, since half a transaction is not something to abandon silently.

When it finishes you see the transaction id and u to undo, the library and playlist index refresh, and you are told whether MPD’s database update was queued. If a commit fails part-way, the view shows what completed, what did not, and the mpdfm recover command to run. See Undo and recover and Safety.

Staged operations survive moving between views and resizing. u also works from the browser (undoing the latest transaction), and :undo <txid> reverses a specific one.

Search, filter and library-wide find

Three tools, all typing into the same line at the bottom of the screen.

KeyDoes
/search the current listing, incrementally
ffilter: narrow the listing to matches until esc
Ffind across the whole library; hits become a flat listing

Search: /

Matches as you type and moves the cursor to the first match. ctrl-n / ctrl-p cycle matches while you are still typing; after enter, n / N do. enter keeps the position, esc returns to where you were.

Filter: f

Hides everything that does not match, and stays on until you press esc. An active filter is always shown in the status bar, so it is never invisible.

Find in the whole library: F or :find <query>

Walks every file, reading tags as needed on a worker with a progress line (esc cancels). The results appear as a flat listing you can mark and stage from like any other — for example, F missing:genre, then a to mark every hit, then e and set the genre.

The query language

Bare words match the file name, the path, and the title, artist, album and genre tags. Several words must all match. Matching is case-insensitive unless the pattern contains an uppercase letter (smart case), and non-ASCII text matches as typed.

doomthe word anywhere
artist:doom, album:"mm..food"that tag; quote values with spaces
genre:jazz, genre:"hip hop"genre

missing:genrefiles with no value for that tag

An empty result says “no matches” rather than showing a blank pane.

Commands, status bar and messages

The command line: :

: opens a line at the bottom. It mirrors the command-line interface — same names, same arguments — so what you know from one carries to the other. A command that does not parse stays open with the reason under it, so you can edit rather than retype. esc closes it; ctrl-u clears it.

CommandDoes
:move <dst> (:mv)stage a move or rename of the marks / cursor row
:organize <template>open the organize view with this template
:find <query> (:f)find across the whole library
:undo [txid]reverse a committed transaction, the latest by default
:messages (:mes)everything said this session, errors included

:q / :q!quit, asking first if operations are staged / quit regardless

:doctor is recognised but not yet wired into the TUI; run mpdfm doctor from a shell for now.

Status bar

The bottom line is always visible and, from left to right, shows the current path, how many items are marked, how many operations are pending, any active filter, the MPD state and the current song when one is playing. MPD shows as ● connected, ○ offline or ◐ updating, refreshed about once a second without ever blocking the interface. MPD being offline does not stop you working: the library is read from disk, and playlist and queue changes are still made on the files.

On a narrow terminal, the least important parts are dropped first.

Help: ?

A scrollable overlay generated from your live keymap, grouped by mode, with the command list. Because it is generated, it shows your rebindings and cannot document a key that no longer exists.

Messages and errors

  • Messages — “committed 20260924T224500Z-a3f1 — 14 files, 2 playlists · u to undo” — appear on the message line and fade. :messages shows the history.
  • Errors open a panel that must be dismissed, with the full message, the path involved and the suggested next step. They are never cut to one line.
  • Progress for scans, finds and commits is a slim line with counts.

Quitting

q quits; with operations staged it asks first. ctrl-c always works (it asks if anything is staged, and leaves on the second press) and cannot be rebound. If music_directory cannot be found, a first-run screen explains where MPDFM looked instead of showing an empty pane.

Safety

MPDFM edits two things you care about: your music files, and the references to them. This page says what it promises, what it keeps so that it can put things back, and — most importantly — how to put things back by hand when MPDFM itself cannot.

If you are here because something went wrong, skip to Recovering by hand. Nothing above it is needed.

In short

  1. Every command that changes anything shows you what it will do first (--dry-run shows exactly the same preview and then stops).
  2. Before the first change, MPDFM copies every playlist it is about to edit, and MPD’s state file, into a backup directory, and writes a journal record saying what it is about to do. Both are on disk, fsynced, before your library is touched.
  3. Every committed transaction can be reversed byte for byte with mpdfm undo. One that a crash cut short is dealt with by mpdfm recover.

Try mpdfm doctor and mpdfm move --dry-run before anything else. Neither writes a byte.

The invariants

These are the properties the test suite exists to defend (docs/PLAN.md §5). A change that violates one is a bug, however convenient.

  1. No filesystem mutation happens outside commit(). Previews, --dry-run, the TUI’s pending view and doctor are pure.
  2. The journal record is durable before the first mutation.
  3. A playlist line is rewritten only on an exact match of the normalized relative path — never a prefix, a substring or a fuzzy one.
  4. Non-track playlist lines are preserved byte for byte: URLs, #EXTINF, comments, blanks, and any line MPDFM has no reading of.
  5. Nothing is read or written outside music_directory, playlist_directory and MPDFM’s own data directory. Symlinks are resolved before this check.
  6. Every file write is atomic: a temp file in the destination directory, fsync, rename.
  7. A cross-device move is copy → fsync → verify → rename → unlink, never a half-finished rename. --verify also hashes the copy.
  8. A path that is not valid UTF-8 is reported and skipped, never guessed at.
  9. Every committed transaction is undoable, and undo checks its preconditions before acting rather than blindly reversing.

Also: nothing is ever overwritten by a move. A collision is a conflict that stops the commit before it starts. And if you set delete_enabled = false, no operation that would remove a file is accepted at all.

What is backed up, and where

MPDFM’s data directory is $XDG_DATA_HOME/mpdfm (~/.local/share/mpdfm by default; mpdfm config show prints the one in use).

<data_dir>/journal/<txid>.json     one record per transaction
<data_dir>/journal/<txid>.steps    each filesystem step, appended as it completes
<data_dir>/backups/<txid>/         what that transaction could not put back from the record alone
    <playlist>.m3u                 each playlist the transaction rewrites, as it was
    state                          MPD's state file (the saved queue), as it was
    files/<relative path>          a file that was deleted
    tags/<relative path>           a file whose tags were rewritten — the whole original

<txid> looks like 20260924T224500Z-00a3f1: a UTC timestamp, then a short suffix. The newest sorts last.

The audio you moved is not copied: a move is a rename, and the record says where it went. Files that were deleted or had their tags rewritten are kept whole under the transaction’s backup directory, because those are the two changes a record alone cannot undo.

Backups are kept for the newest backup_keep transactions (50 by default). Older backup directories are removed; the journal records are never removed, so mpdfm undo --list can still tell you why an old transaction can no longer be undone. A transaction that is still pending or failed is never pruned.

The order of a commit

1  re-check the plan against a fresh scan        nothing changed
2  copy the playlists and state file to backups  nothing changed
3  write the journal record, status "pending"    nothing changed
4  do the filesystem steps, journaling each one  the library changes
5  rewrite the playlists and MPD's state file    the references change
6  mark the record "complete"
7  ask MPD to rescan

Steps 1–3 can fail as often as they like and leave the library exactly as it was. From step 4 on, the record says what had been done — or, at worst, is one step behind, because a step is logged after it happens and a crash can fall between the two. It is never ahead.

So a crash leaves the record pending, and the filesystem somewhere between the start and the end.

Detecting an interrupted commit

$ mpdfm undo --list          # lists every transaction and its status
$ mpdfm recover              # surveys, then offers to roll back what a crash left

Without the binary:

grep -lE '"status": *"(pending|failed)"' ~/.local/share/mpdfm/journal/*.json

Any file it prints is a transaction that did not finish. (failed means MPDFM stopped on an error rather than being killed; the recovery is identical.)

Recovering by hand

Use this when mpdfm recover will not run — a bug, a version mismatch, a binary you no longer have. It is the same procedure MPDFM follows, spelled out.

Everything you need is two things on disk: the journal record, and the backup directory it names. You need nothing from MPDFM, but jq makes the record easier to read. Throughout, set:

DATA=~/.local/share/mpdfm                       # or: the data_dir from config.toml
TX=20260924T224500Z-00a3f1                      # the transaction you found above
REC=$DATA/journal/$TX.json
BAK=$DATA/backups/$TX

0. Stop, and stop MPD

  • Do not run MPDFM, and do not commit anything else, until you are done.
  • Stop MPD (systemctl --user stop mpd, or mpd --kill). MPD overwrites its state file from memory when it shuts down, so a state file restored behind a running MPD is thrown away — and a playlist you restore may be saved over by it.
  • Check the backup exists. If $BAK is not there, stop: the transaction never got past step 2, nothing was changed, and the record is just a leftover. Go to step 6.
ls "$BAK"
jq '{status, music_dir, playlist_dir, ops}' "$REC"

music_dir and playlist_dir in the record are the absolute paths this transaction used. Every library path in steps is relative to music_dir.

1. Read what the transaction did

jq -r '.steps | to_entries[] | "\(.key)\t\(.value.done)\t\(.value.step)"' "$REC"

Each step is one of these, in the order it ran. .done is whether the journal heard that it finished — which may be one step behind reality. The disk is the authority: for each step, look.

StepWhat it didUndo it by
MkDir { at }created a directoryrmdir it, if empty and it did not exist before
RenameFile { from, to }moved a file or directorymv "to" "from"
CopyDelete { from, to }moved it across filesystemsmv "to" "from" (or cp then rm across the boundary)
RemoveFile { target, backup }deleted a file, keeping it in backupmv "backup" "target"
WriteTags { target, backup }rewrote a file’s tags, keeping the original in backupcp "backup" "target"
ExtractArt { from, to }wrote a new image file torm "to" (it did not exist before)
RmDirIfEmpty { at }removed an emptied directorymkdir -p "at"

A step is done if the state it produced is on disk: a RenameFile whose from is gone and whose to exists; a RemoveFile whose target is gone. A step that is not done needs nothing undone. A step where both from and to exist, or neither does, is not something to guess about — see If the disk does not match.

2. Put the playlists back

For every entry in playlist_edits — and only those — copy the backup over the file the record names:

jq -r '.playlist_edits[] | "\(.file_name)\t\(.real_path)"' "$REC"

# for each line it prints:
cp -p "$BAK/<file_name>" "<real_path>"

real_path is where the playlist really lives. For a symlinked playlist that is the file the link points at, not the link, and restoring it there is correct.

Restoring a playlist is safe whether or not its edit was ever applied: the backup is what it was before.

Do not restore playlists the record does not list. The backup directory may hold copies of playlists the transaction never changed, and MPD or you may have edited those since.

3. Put MPD’s saved queue back

Only if state_edits is not empty:

jq '(.state_edits | length), .state_backup' "$REC"   # how many edits, and the backup's name

cp -p "$BAK/state" ~/.config/mpd/state     # your state_file, from config.toml or mpd.conf

MPD must be stopped (step 0). If state_edits is empty, MPDFM did not change that file, and you must leave it alone: MPD has rewritten it since.

4. Put the library back

Undo the done steps from the table above in reverse order: the last step that ran is the first you undo. Work from music_dir:

cd "$(jq -r .music_dir "$REC")"
jq -r '.steps | to_entries | reverse[] | "\(.key)\t\(.value.step)"' "$REC"

An example, a directory move that was interrupted after the files had been moved but before the old directory was removed:

2  RmDirIfEmpty { at: "rock/A" }              -> not done: rock/A still exists   (nothing to undo)
1  RenameFile { from: "rock/A/01.flac",
                to:   "rock/B/01.flac" }      -> done                             mv rock/B/01.flac rock/A/01.flac
0  MkDir { at: "rock/B" }                     -> done                             rmdir rock/B

Never overwrite: if the place you are moving something back to already has a file, stop and look. It means something else wrote there after the crash, and only you can say which one is right. mv -n refuses to overwrite and is the right habit for every command here.

A WriteTags backup is the whole original file, so cp over the target puts its tags, artwork and audio back exactly. For a RemoveFile, mv the file out of the backup and, if its directory was removed too (RmDirIfEmpty), mkdir -p that first.

5. Check

mpdfm doctor --check references     # if the binary runs; every playlist line should resolve

Without the binary: every line in the restored playlists that names a file should exist under music_dir:

grep -v '^#' "<real_path>" | grep -v '^[a-z]*://' | while IFS= read -r p; do
    [ -e "$(jq -r .music_dir "$REC")/$p" ] || echo "missing: $p"
done

Then start MPD again and let it rescan (mpc update).

6. Close the record

So that MPDFM stops reporting it, and so that nobody later runs recover on a transaction you have already dealt with:

mkdir -p "$DATA/journal.handled"
mv "$DATA/journal/$TX".* "$DATA/journal.handled/"

Leave $BAK where it is until you are sure everything is right. It is the only copy of the originals.

If the disk does not match

The tidy case — each step done or not done — is what a crash between steps leaves. Two other cases are rare and worth stopping for:

  • Both from and to exist. Either the step was a copy that did not get to delete the source (cross-filesystem move), or something recreated one of them. Compare them (cmp). If identical, the copy completed: remove from or to as you prefer, then continue. If not, you are looking at two different files — keep both until you know which is which.
  • Neither exists. Look in $BAK/files/ and in your trash before concluding anything. Do not recreate a file from memory.

When in doubt, do less. A half-undone transaction with the journal and backups still in place can be finished tomorrow; a guess cannot be taken back.

What MPDFM does not protect against

  • A deliberate mpdfm undo --force, which skips what has changed since and reports it. That is what it is for.
  • Anything you do to the library yourself between a commit and its undo. undo checks that the files are still as the commit left them; if they are not, it stops and tells you which, instead of overwriting your edit.
  • A disk that lies. fsync is as good as the drive’s promise.
  • Backups older than backup_keep transactions. After that, undo says the backup was pruned and refuses rather than pretending.

MPDFM — Design Plan

MPD File Manager: a terminal application for editing music metadata and re-organizing an MPD music library without breaking the playlists, the saved queue, or anything else that stores a path.

Written during the design session of 2026-09-24. This document is the architectural reference; ROADMAP.md holds the ordered task list and status.

1. Problem statement

MPD identifies every track by its path relative to music_directory. That relative path is duplicated in at least three places outside the audio file:

LocationFormatCount in this library
~/.config/mpd/playlists/*.m3uone relative path per line231 track entries across 17 playlists
~/.config/mpd/stateN:relative/path lines in the saved queue61 entries
~/.config/mpd/databaseMPD’s own index~2 800 tracks

Moving or renaming a file with mv silently invalidates every one of those references. The database recovers on rescan; the playlists and the saved queue do not. MPDFM exists to make the move and the reference-rewrite a single atomic, reversible operation.

The second goal is ordinary metadata editing (ID3v2 for mp3, Vorbis comments for FLAC), single-file and in bulk, because bad tags are what make a library need re-organizing in the first place.

2. Decisions

#DecisionRationale
D1Rust, ratatui + loftyUser reads Rust. lofty writes ID3v2, Vorbis comments and MP4 atoms with no C dependency; Go’s equivalent needs cgo + system taglib, which would undercut the headline feature.
D2Core library + CLI + TUIAll logic lives in mpdfm-core with no terminal and no clap. The CLI makes the dangerous paths testable and scriptable; the TUI is a second front-end over the same API.
D3Manual moves first, template-driven organize secondBoth share one safe-move engine, so no work is wasted. Manual is the primitive; templates are a plan generator on top.
D4Rewrite playlists on disk, with backups + journal + undoMPD’s protocol has no atomic path-replace and cannot see playlists it hasn’t indexed. Direct file editing is the only approach that can be transactional.
D5mp3 + FLAC in v1 (m4a free via lofty, untested)2 797 of ~2 800 audio files. A tool that skipped FLAC during a reorg would be a trap.
D6MPD connection optional and non-fatalFilesystem is the source of truth. If 127.0.0.1:6600 answers we trigger update after a commit and warn about queue conflicts; with MPD stopped everything still works.
D7Stage → preview → commitNothing touches disk until confirmed. The preview shows filesystem changes and which playlist lines will be rewritten. Every commit is journaled and undoable.
D8Vim-style keys, configurableConsistent with rmpc, which the user already drives. Remappable from config without recompiling.
D9Tasks as markdown in docs/tasks/Versioned with the code, readable offline, no auth needed to resume work in a later session.

Explicitly out of scope for now: MusicBrainz / AcoustID lookup, in-app playlist authoring (create/reorder/dedupe), audio playback. Cover art and a library doctor are in scope as later phases.

5. Core model

Identity: RelPath

The canonical identity of a track is its path relative to music_directory, UTF-8, /-separated, no leading ./, no .., never absolute — because that is exactly what playlists, the state file and MPD all store. A newtype enforces this so a raw PathBuf can never leak into a playlist line. A leading ./ is rejected rather than normalized (task 02), so every string the newtype accepts renders back byte-identically.

Playlist entries are byte-preserving

#![allow(unused)]
fn main() {
enum Entry {
    Blank,
    Comment(String),                                   // "# Liquid Drum & Bass"
    ExtM3u,                                            // "#EXTM3U"
    ExtInf { duration: i64, title: String, raw: String },  // "#EXTINF:-1,Lofi Radio"
    Url(String),                                       // "http://ice1.somafm.com/…"
    Track { rel: RelPath, cue: Option<String>, raw: String },
    Unparsed(String),                                  // "/absolute/path.mp3"
}
}

Every variant keeps enough information to be written back byte-identically. Only Track entries whose rel exactly matches a moved file are ever rewritten; everything else round-trips untouched. cue holds the trackNNNN suffix of an MPD CUE virtual track, so album.flac.cue/track0017 moves as a unit. Unparsed is the line MPDFM has no reading of — an absolute path, a ./ path, a stray carriage return — preserved rather than dropped, because dropping a line the user wrote is a data-loss bug (task 06).

Operations and the two-phase commit

#![allow(unused)]
fn main() {
enum Operation {
    MoveFile   { from: RelPath, to: RelPath },
    MoveDir    { from: RelPath, to: RelPath },
    Delete     { target: RelPath },
    WriteTags  { target: RelPath, changes: TagDelta },
}

Plan { ops: Vec<Operation> }
  .validate(&Library, &PlaylistIndex) -> Effects    // pure; no disk writes
Effects {
    fs_changes:      Vec<FsChange>,
    playlist_edits:  Vec<(PlaylistPath, Vec<LineEdit>)>,
    state_edits:     Vec<LineEdit>,                  // MPD saved queue
    conflicts:       Vec<Conflict>,                  // blocks commit
    warnings:        Vec<Warning>,                   // informational
}
  .commit() -> TransactionId
}

commit() is deliberately two-phase so that a crash mid-operation is recoverable:

  1. Copy affected playlists (and the state file) into ~/.local/share/mpdfm/backups/<txid>/.
  2. Write journal record with status pending, including every backup path. (This way round: a crash between the two leaves an orphan backup directory, which is garbage, where the other order would leave a record naming backups that are not there, which undo would believe. Task 11.)
  3. Execute filesystem operations in order, appending each completed step to the journal.
  4. Rewrite playlists and the state file atomically (temp file + rename in the same directory; resolve symlinks first so Radios.m3u edits the dotfiles target, not the link).
  5. Mark journal record complete.
  6. If MPD is reachable, update the affected directories.

A pending record found at startup means a previous run died, and mpdfm recover is what deals with it: it works out from the disk what the transaction actually managed — the journal can be one line short of the truth, never more — and then rolls it back (the default) or finishes it. mpdfm undo deliberately refuses a record that is not complete and says so, because undo believes the record and a pending one is not a finished account of anything. Task 12.

Safety invariants

These are the properties the test suite exists to defend. Any change that violates one is a bug regardless of how convenient it is.

  1. No filesystem mutation happens outside commit().
  2. The journal record is durable before the first mutation.
  3. A playlist line is rewritten only on an exact normalized-RelPath match — never a prefix, substring or fuzzy match.
  4. Non-track playlist lines (URLs, #EXTINF, comments, blanks) are preserved byte-for-byte.
  5. No operation may read or write outside music_directory, playlist_directory and MPDFM’s own data dir. Symlinks are resolved before this check.
  6. Every file write is atomic: temp file in the destination directory, fsync, rename.
  7. Cross-device moves are copy → fsync → verify size/hash → rename → unlink, never a partial rename failure left half-done.
  8. A path that is not valid UTF-8 is reported and skipped, never guessed at.
  9. Every committed transaction is undoable, and undo verifies preconditions before acting rather than blindly reversing.

8. Testing strategy

The move engine is the part that can destroy data, so it is tested first and hardest, before any UI exists.

  • Fixture builder — construct a synthetic library in a tempfile::TempDir: genre dirs, scene-style album names, non-ASCII names, a multi-disc album, aux files, a symlinked playlist, a CUE virtual track, a radio URL playlist, and a deliberately broken reference. Real mp3/flac files are generated with ffmpeg (present on this machine) or committed as tiny fixtures.
  • Round-trip property: parse → serialize any playlist ⇒ byte-identical.
  • Move invariants: after any committed move, every playlist entry that resolved before still resolves, and the set of referenced inodes is unchanged.
  • Undo invariants: commit → undo ⇒ filesystem and every playlist are byte-identical to the starting state.
  • Crash injection: abort between phases of commit(); the journal must leave the library recoverable.
  • Snapshot tests (insta) for Effects previews and CLI output.
  • No test may touch the user’s real ~/Music or ~/.config/mpd. A guard in the test harness asserts every path used is inside the temp dir.

Open questions to revisit

  • Chained moves (a → b, b → c) in one plan: order them or reject them? Decided in task 10: ordered. They are topologically sorted; a ring is a Conflict::Cycle; every operation’s source must exist in the library as it is now, which removes the two-hop reading. Rationale in ops::plan’s module docs.
  • Redo: a command of its own, or undo-of-an-undo? Decided in task 12: undo-of-an-undo. Every record carries a direction, an undo writes one of its own that says reverse, and undoing that executes its steps forward again. The direction flips every time, so mpdfm undo twice in a row is a redo and there is no second command that can disagree with the first.
  • Journal flush: after every step, or in small batches? Decided in task 11: after every step, appended to a second file. Rewriting the whole record each time is quadratic (115 s extrapolated for the 4 500 steps a real whole-library reorganization produces); one appended line per step is flat and keeps the invariant batching would have broken. Measurements in task 11’s decisions.
  • Is a scan cache needed to keep the TUI responsive (PLAN.md §7, ~/.cache/mpdfm/scan.json, “only if scanning proves slow”)? No. Measured in task 15 with the release binary: the real library’s 3 132 files across 27 GB scan in 10 ms. Task 20 can rescan on a keystroke and the cache should stay unbuilt. Numbers in task 15’s hand-verification section.
  • FLAC multi-valued fields: Vec<String> throughout, or join-and-remember? Decided in task 16: an ordered list in every text field (tags::Values). Join-and-remember needs the same two pieces of information and then has to guess which semicolons were separators on the way back out. The tag editor still shows one row per field, through Values::joined; 16 of the 2 808 real files are multi-valued.
  • Whether doctor should report the 25 files holding frames no ID3v2 writer will emit — an invalid TDRC, a WXXX with no description, a v2.4-only frame in a v2.3 tag. Task 17 measured them and leaves them alone; naming them is task 29’s business, not the writer’s.
  • How much of --deep duplicate detection is worth it on a 2 800-file library (task 29) — measure before building the hash pass. Cheap, because size goes first. Only 6 of the real library’s 2 809 audio files share a size with another, so --deep hashes 6 files and adds ~30 ms; none of them are identical. It stays opt-in anyway, because a library of rips from one source can share sizes far more often. Numbers in task 29.
  • Whether to add a mpdfm find CLI command mirroring the TUI query parser (task 25) — cheap once the parser is in core.

Added
